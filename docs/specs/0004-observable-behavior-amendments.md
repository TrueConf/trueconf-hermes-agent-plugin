# TrueConf Observable Behavior — Amendments

Status: **implemented**

Amends: [docs/specs/0001-observable-behavior.md](0001-observable-behavior.md)

This document ratifies behaviors introduced after the initial 0.1.0
implementation (October 2026): the SDK 1.5.0 release renamed `reply_markup`
to `buttons`, a security review prompted a group-prompt fallback and prompt-id
changes, and a capability-parity check against the reference Telegram adapter
added capability flags and status-bubble deduplication. Each section below is
a normative amendment to spec 0001 unless stated otherwise.

## 1. Button prompts are direct-chat only; groups get numbered text

Spec 0001 §9 describes prompt delivery without distinguishing chat types.

The SDK `CallbackQuery` carries no clicker identity, so in group and channel
chats any member could resolve an approval, slash confirmation, or clarify.
Amendment:

- In direct P2P chats, clarify, approval, and slash-confirm prompts render as
  inline keyboards, as before.
- In group and channel chats, the same prompts render as text with a numbered
  option list. A reply consisting of an option number (or the exact option
  label) is consumed by the Plugin and resolved through the same Hermes
  primitives (`resolve_gateway_approval`, `slash_confirm.resolve`,
  `resolve_gateway_clarify`); it MUST NOT also be forwarded to the agent.
- A text prompt answer is consumed only when the sender passes the Plugin's
  early authorization check (`authorized is True`). All other messages keep
  the §9 flow, including final authorization by Hermes.
- One pending text prompt is kept per chat; a newer prompt replaces the older
  one. The pending state is in-memory and follows the same restart semantics
  as the button state.

This is an intentional exception to S4/§9 ("every otherwise supported message
is submitted"): a consumed prompt answer is submitted to Hermes as a
resolution, not as a message.

## 2. Prompt request ids are unique across restarts

Approval prompt ids are generated by the Plugin as `uuid4().hex`. A
monotonic counter would re-issue ids after a gateway restart while old button
messages remain clickable, allowing a click on a stale prompt to resolve a
fresh approval it never belonged to. Slash-confirm and clarify ids continue
to come from Hermes. A prompt request id MUST NOT contain `:` — `custom_data`
is parsed with `split(":", 2)`, and prompts whose ids contain a colon are
rejected at send time with a failed `SendResult`.

## 3. The Plugin owns message chunking

Spec 0001 §3.1 attributes "chunking and send retry" to Hermes Core. Since
ADR 0004 and spec 0002 §9 the Plugin translates and splits content itself,
and the adapter now declares:

- `splits_long_messages = True` — Hermes delivers full payloads (notably cron
  output, which is otherwise truncated at 4000 characters with a footer) and
  the Plugin chunks via the SDK's `safe_split_text` at the 4096-character
  limit;
- `MAX_MESSAGE_LENGTH = 4096`;
- `supports_code_blocks = True` — the gateway may emit fenced code blocks in
  tool-progress messages; the formatter continues to translate them per spec
  0002 §4.2 (multi-line `<i>` block).

## 4. `reply_to_mode` — Required becomes configurable

Spec 0001 §5.2 marks `send(..., reply_to=...)` → native reply as "Required".
It stays the default, but is now governed by the `reply_to_mode` platform
setting:

- `first` (default) — current behavior: the first delivered message of a send
  is anchored to the trigger message; continuation chunks chain to the
  previous chunk.
- `all` — every chunk of a chained send is anchored to the trigger message.
- `off` — no reply anchors are sent.

`reply_to_mode` is a validated configuration key (`§8.4`): values outside
`first`, `all`, `off` are a configuration error. YAML `platforms.trueconf`
accepts it.

## 5. Status bubbles are deduplicated

The adapter implements `send_or_update_status(chat_id, status_key, content)`:
the first send for a `(chat_id, status_key)` pair delivers a message, and
later calls with the same pair edit that message in place instead of
appending new ones. Only single-chunk status sends are cached — a shrunken
multi-chunk edit would leave stale heads behind (accepted trade-off, see
AGENTS.md). On edit failure the cached id is dropped and the status is sent
fresh. The cache is bounded (256 entries).

## 6. `disconnect()` is time-bounded

Spec 0001 §7.4 lifecycle rules are unchanged, with one addition: the SDK
shutdown call is wrapped in a 10-second `asyncio.wait_for`, and the gateway
run task is cancelled before being gathered. A wedged WebSocket transport
must not hang `disconnect()` (and with it the standalone sender that waits on
the disconnect task).

## 7. Typing indicator clarification

Spec 0001 §5.2's "refreshed for the duration of Hermes response generation"
is implemented as: the Plugin starts one SDK `ChatActivitySender` per chat
and leaves it running for the turn; the SDK owns the server-provided
`retryAfter` cadence. Later `send_typing` calls for an active sender are
no-ops.
